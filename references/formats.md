# 대체 출력 형식 템플릿

**이 파일의 형식 1~4는 모두 사용자가 명시적으로 요청할 때만 만든다.** 기본 산출물은 SKILL.md Step 5의 6개 섹션 md 파일이다. 모든 형식에서 지켜야 할 것: 실측값은 **굵게**, 0도 굵게. 리스크 작업은 발단→조치→움직였나 구조.

## 형식 4. 전체 공유용 간소화 표 (요청 시에만, 노션 복붙용)

4행 표를 마크다운 코드블록으로 제공한다. **각 행은 반드시 한 줄** — 셀 안에 실제 줄바꿈이 있으면 노션이 표로 인식하지 못한다. `<br>`도 동작하지 않는다. 붙여넣은 뒤 shift+enter로 줄을 나누라는 안내를 코드블록 밖에 한 줄 붙인다. 셀 안 구조는 **①②③ 항목 + • 하위 항목 + 굵기**로 잡는다 (노션 붙여넣기에서 유지됨).

```markdown
| 항목 | 작성 내용 |
| --- | --- |
| 1. 이번 주 끝낸 일 | **① <신규 구축 작업>** — ... **② <신규 구축 작업>** — ... **③ <장애·이슈 대응 통합 항목>** — ... |
| 2. 움직인 수치/변화 | **① <전후 비교 숫자가 제목>** • 문제: ... • 해결: ... • 움직임: ... **② ...** **③ <기대되는 변화>** • ... • 확인 방법: ... **④ 총량** — ... |
| 3. 막힌 것/리스크 | · **[결정] ...** · **[리스크] ...** |
| 4. 다음 주 가장 중요한 일 | **① ...** **② ...** |
```

### 1행 (이번 주 끝낸 일)

- 완료 기준 — 검증까지 끝난 것만. 미검증 항목은 제외. 배포 상태(dev/운영, 배포일)는 사실대로 명시하고, 배포 시점은 추측하지 말고 확인한다.
- **순서: 신규 구축·기능 작업 먼저, 장애·이슈 대응은 뒤에.**
- **한 이슈에서 파생된 작업은 한 항목으로 통합한다** — 장애 해결 + 전수조사 + 원인 확정 실험 + 후속 조치는 별도 항목이 아니라 하나의 스토리(발생 → 원인 → 해결 → 재발 방지)다.
- 핵심만 간단명료하게. 상세 수치는 2행에 맡기고 1행에서는 뺀다. "왜 중요한가"는 항목당 최대 한 문장.
- VOC 대응 중 원인 특정 불가로 끝난 건은 "원인을 못 찾았다"가 아니라 **"재발 시 바로 특정할 수 있도록 관측 지점을 마련했다"** 프레임으로 쓴다.

### 2행 (움직인 수치/변화) — 비개발 직군 언어로, 핵심만

- **전후 비교 숫자를 항목 제목으로** 쓴다 (예: "상품 목록 조회 3초 → 0.2초, 약 15배 개선").
- 기술 용어 금지. 불가피하면 비유 하나로 대체한다 (색인 = 책 뒤 찾아보기 / 포인트 원장 = 적립·차감을 한 줄씩 적어 둔 장부). 임시테이블·filesort·서브쿼리·와일드카드 같은 단어가 남아 있으면 다시 쓴다.
- **해결 완료 건**: 문제(실측 크기) / 해결(검증 사실) / 움직임(전후 비교) 3요소, 각 한두 문장.
- **기대되는 변화**: 지표를 보이게 만든 작업(대시보드·자동 리포트·관측 로그)은 "수동 → 자동", "확인 불가 → 단계별 추적 가능" 같은 상태 전환으로 쓰고 **확인 방법 한 줄**(다음 주 무엇을 보면 검증되는지)을 붙인다.
- 프로덕트 지표(가입·거래·퍼널)와 원인 미확인 수치는 넣지 않는다. 미확인 건은 "수치는 확인 후 공유 예정".
- **총량 한 줄**: 커밋 수 · +줄/−줄 · 파일 수 · 갈래별 비중. 코드로 안 남은 큰 작업(DB 인덱스, 실험, 문서)이 있으면 한 문장으로 짚는다.

### 3행 (막힌 것/리스크)

- 전부 [결정]/[리스크]/[협조] 태그를 붙여 "회의에서 답을 받아낼 항목"으로만 구성. 단순 걱정거리 금지.
- **비개발 직군 언어로 간단명료하게.** 각 항목은 세 질문에만 답한다: 왜 지금은 문제가 아닌지 / 언제·어떤 조건에서 문제가 되는지 / 무엇을 해야 하는지.
- 원인 미확인 관측치는 숫자를 빼고 "원인 미확인 상태라 수치는 확인 후 공유 예정"으로 쓴다.

### 4행 (다음 주 가장 중요한 일)

- 우선순위 1~2개만. 발견만 하고 미해결인 문제는 여기서 "확정하고 착수" 진행형 프레임으로 흡수한다.
- 이미 끝난 일을 다음 주 일로 남겨두지 않는다 (예: 배포가 이미 됐으면 "배포"가 아니라 "배포 후 검증·마무리"로 고쳐 쓴다).

### 수정 요청 대응

- 사용자가 특정 행/셀만 고쳐달라고 하면 그 부분만 코드블록으로 준다. 노션 셀 안에 직접 붙여넣는 경우이므로 여러 줄로 써도 된다 (셀 안 붙여넣기는 줄바꿈 유지).
- 통합·압축·순서 변경·비개발 언어화 요청이 이어지는 것이 정상 흐름이다. 수정 시 바뀐 부분만 다시 준다.

## 형식 1. 상세 회고 문서 (요청 시에만, md 파일)

```markdown
# 금요일 회고 — 무엇이 움직였나 (<이름>, <기간>)

> "무엇을 했나"가 아니라 "무엇이 움직였나"로 정리. <기준일> 운영 DB를 직접 집계한 결과 기준 — <핵심 결과 한 줄>.

## 1. 이번 기간 핵심 목표 1개

**<모든 작업이 수렴하는 목표 한 문장>**

## 2. 작업 → 지표 매핑

| 작업 | 커밋 | 연결 지표 | 분류 |
|---|---|---|---|
| ... | 날짜 (n개) | ... | 임팩트 높은 일 / 검증하는 일 / 유지 업무 |

\* **임팩트 보존**: 지표를 올리는 일이 아니라, 지표가 한 번에 무너질 **실재하던** 리스크를 제거한 일.

## 3. 무엇이 움직였나 — 영역별

**측정 방법**: <기준일> 운영 DB에서 도메인별 테이블을 직접 전수 집계했다. (사용한 쿼리는 §부록)

### A. <작업명>

**만든 것** / **연결 지표** / **움직였나** (실측값 — 무엇을 어떻게 세었는지 / 회의에서 말할 것 / 제안)

(리스크 제거 작업은: **발단** / **조치** / **분류** / **남은 리스크**)

### 서비스 고정 지표 (상세 문서 전용)

서비스의 핵심 퍼널을 매번 같은 기준으로 센다. 예(가상의 쇼핑 서비스): 공급 퍼널(`seller_applications` → `stores`) / 수요 퍼널(`carts` → `orders` → `payments`(결제 완료 상태) → `reviews`) / 프로모션. 직전 회고 실측값을 기준선으로 명시하고 병목 이동을 해석. 테이블마다 시간대(UTC/KST)가 다를 수 있으니 엔티티로 확인한 뒤 집계한다.

## 4. 부록 — 측정에 사용한 쿼리
```

## 형식 2. 회의록용 요약 (요청 시에만, 채팅 출력)

번호 리스트. 항목당: 작업명 — 분류 / 연결 지표 / 움직였나. 리스크 작업은 발단·조치·핵심 주장 추가. 마지막에 "한 줄 요약".

## 형식 3. 백엔드 직무별 공유 프레임 (요청 시에만)

핵심 공유 항목(완료한 API/서버/DB/어드민 작업, 안정성 개선) / 수치·근거(장애 건수, 배포 성공률, 운영 효율 — 측정 체계 없는 항목은 "이번 주 측정 체계 없음 → 다음 주 과제"로 솔직하게) / 다음 주 연결 질문(우선순위 1~3개).
